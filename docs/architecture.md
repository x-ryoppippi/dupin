# Architecture

The search and ranking model must remain independent of UI frameworks and operating-system APIs. Native providers own the macOS boundary; the thin UI layer adapts input and renders results so that the UI framework can change without replacing the model.

## Providers

Every source of results is a `Provider` that streams batches of `Item`s and stops when its request is superseded. A `Request` carries the query, candidate budget and an optional `page` for a pushed view. Apps, file names and file contents each have a provider. Each loaded [extension](./features/extensions.md) has a provider that runs its guest and turns the returned views and actions into items. For a `package.json` with a `dupin` key, Dupin only reads the package's files, as `dupin-js-runtime`'s bounded `Sources`. The extension host, Dupin's executable started with `--extension-host`, which confines itself with the macOS sandbox before touching guest code, erases the types of TypeScript modules with the oxc parser and compiles them on QuickJS-ng through `dupin-js-runtime` when the scanner loads the folder and runs each query in a fresh runtime with its own heap, stack, deadline and promise-job limits. `dupin-extension-host` starts one such process for each package to compile, so no other package's code reaches the bytecode it returns, and a resident process, on first use, for the calls of each trust domain: one shared by the bundled packages and one for each other package, since a process answers requests with the authority of the package it runs. It talks to them over a Unix socket and sends the bytecode, which Dupin keeps as opaque bytes, with every call. It kills the process when a compile or call overruns its deadline, ignores cancellation, outgrows its memory allowance or dies; the next call starts another. The host answers in `dupin-plugin-protocol` rows, so copy and URL actions reach the session as a built-in's do.

Apps, file names, file contents, folder browsing and recent items are native sources. Each feature's registration names its sources (`features::Feature::sources`) with the command each answers and, for a source that matches its own candidates, the matcher it starts with. The host resolves that name in `dupin-core::filter::Filters` (`builtin.fuzzy`) and hands the source its `Matcher`, so apps and folder browsing rank through it; the Spotlight sources match through Spotlight's index and keep their own ranking. A source never builds a row's actions: it says what the row is, as a `dupin-core::kind::Subject` (text, a URL, a file or folder, or an app), and the `Kind` registered for it in `Kinds` returns the actions, Enter's and ⌘Enter's, and what Send to… offers for the row's payload, so every source of files shows the same file actions. `dupin-mac::kinds` supplies the macOS share services and tells folders from packages. An extension row's text and URL resolve through the text and URL kinds; its `file` is a path the guest chose, so it gets no file-kind actions.

An `Item` owns the runtime-independent `dupin-plugin-protocol::View`: Text (title/subtitle), Detail (title/body), or Pair (source/result). It also carries its stable ID, icon path, matched title characters, optional score, action list and primary/alternate action IDs. `display_title()` returns the Text/Detail title or Pair source. Explicit `record_usage` metadata controls history recording; apps/files opt in and dictionary results opt out, independently of view.

A provider that groups or lays out its rows overrides `Provider::search_batches`, which hands over a `Batch`: rows, an optional section title, and a `Detail` for any row that should show as a page. A `Detail` has a title, labeled metadata and a Markdown body that `dupin-core` parses once, with pulldown-cmark, into a bounded document of headings, paragraphs, lists and code blocks with bold, italic, code and link runs. Input past 32 KiB, blocks past 512 and lists nested past three levels are cut or flattened. Only http and https links are pressable; raw HTML and other schemes stay inert text. The session keeps sections and details beside the rows, by origin and item ID, so ranking, selection restoration and back navigation treat a sectioned row like any other. A batch can ask for its details to show only while their row is selected, so a long list stays a list. The row's own `View` stays the plain-text form for the CLI and snapshots.

A source that hands over its whole list rather than answering each query keeps it in a `dupin-core::catalogue::Catalogue`: rows with keywords, sections and details, changed whole or by ID within row and byte limits, and matched with the same fuzzy matcher apps use. Each name is folded once when its row arrives, a keystroke scores every row without allocating and finds the highlighted characters only for the rows shown, and an empty query lists the rows in order under their sections. An extension's `items()` fills one per loaded package revision, through the extension host, on first use, after its `ttl` or when one of its action handlers invalidates it; typing never calls the package. A package that asks for it also gets a second, keyword-less command in the default providers after apps, which matches the same catalogue, so the main search never hands the package a query.

The host renders each item in declared order. All-text lists retain fixed-height virtualisation; a sectioned list adds a heading row where the section changes and lays out every row, and mixed results use a bounded scrolling column with selectable detail/pair cards and stable row/action anchors. Text rows keep an icon column only when some row in the list has an icon, so an icon-less list such as calendar events or snippets starts its titles at the row's edge while a mixed list keeps them aligned. Keyboard selection moves between rows only; a heading shares its first row's key, so revealing that row shows the heading too. Rows are keyed by item, so the list doesn't anchor its scrolling to the row at its top, which would follow that row down through the next query's results. Each answer that changes the results shows the selected row: the first row of a new query, or the row the user chose when the same search refreshes or a view they return to searches again. A list scrolled for the results it replaces scrolls to it; a list at its top whose first row is selected asks for no scroll, which would slow the frame. A pressed link goes back to the session, which opens it only if the current row's detail links to it.

Registered routes and shared internal views advance the plugin migration. Native providers still call OS APIs directly. `dupin-broker` holds the extension authority model, with declared capabilities, per-revision grants and revocable permits ([capability broker](./capability-broker.md)). A JavaScript guest reaches host services only through `dupin-extension-bridge`: its requests cross the helper's socket to the app, where a session made for that call checks each with the broker, under the trigger the app saw, before `dupin-host-services` or `dupin-extension-http` acts, and drops the result if authority changed meanwhile. Native providers don't go through it.

Extensions come from two folders, each with its own scanner and watch. Bundled ones ship in `Dupin.app/Contents/Resources/extensions` (the repository's `extensions/` for a build from the source tree) and are always scanned; the user's `extensions/` beside config.toml is scanned while `extensions = true`. `build.rs` seals the bundled packages: it records the content hash (`dupin_extension_install::content_hash`) of each folder in the repository's `extensions/`, and the bundled scanner skips any folder that isn't one of those or no longer matches, as the user scanner skips one that no longer matches the installed extensions list (the `extensions` and `extensions-local` namespaces of encrypted storage). `extensions::packages` merges the two catalogues once the bundled one has arrived: a user package with a bundled package's `name` replaces it, and bundled ones register first, so they keep their keywords. Each package's revision is a BLAKE3 hash of its `package.json` and every module Dupin runs. The broker knows a bundled package as `bundled:<name>`, which no package.json name can be, and a user copy by that id only while its revision is the shipped one, so grants and choices never pass between a bundled package and a folder package reusing its name. The app tells the broker bridge each bundled revision (`Bridge::set_bundled`) and installs the active revision of every package, so a bundled package is on and pre-granted exactly while the active copy is the one that shipped. A package runs unless the user or the declared base turned it off; one never turned on answers its keyword but can use no host service. Settings → Extensions shows both, marks an enabled one that lost its keyword as not answering, and saves the switches through the bridge in the `extension-grants` namespace with `Broker::change_saved`, so a switch that can't be saved changes nothing.

Extension authoring runs outside the launcher. `dupin-ext-sdk` backs `dupin ext new`, `build` and `dev`: it scaffolds packages with the declarations in `sdk/dupin.d.ts`, bundles packages with npm dependencies with the author's own Rolldown, and publishes development revisions behind a symlink the extensions scan already follows. It checks packages with `dupin-js-runtime`, as the launcher loads them. Dupin never bundles, downloads a bundler or type-checks at run time; extension providers load the JavaScript and erasable TypeScript these commands produce or check.

## Searching off the main thread

Trusted [script commands](./features/scripts.md) use a separate native execution path. Discovery only reads bounded headers; activation runs the executable directly on a worker with bounded output and an owned process group. The lifecycle lock serializes spawning and group registration with synchronous quit cleanup. Script operations are absent from the guest protocol.

Each provider runs on its own long-lived thread behind a `Searcher`. The newest request wins: queued requests never start, a running one sees `Request::is_cancelled`, and its late batches are dropped before they reach the UI. A dedicated thread, rather than a pool, lets the Spotlight provider turn that thread's run loop, which `NSMetadataQuery` delivers through.

Candidate budgets and display limits are separate. The worker enforces each request's cumulative output budget; the session stores at most that many unique candidates, applies usage ranking, then cuts each provider and the merged list to their display limits. A chosen row or open action menu keeps its target in a visible slot while ranking changes, except when the only available slot belongs to the pinned provider. Automatic first-row selection does not pin a weak result indefinitely.

## The session

`Session` is the launcher's state machine. The host registers commands and their routes. The UI hands the active session query edits and key intents. The session answers with effects such as starting or cancelling a search, running an action, clearing the field, hiding the panel or keeping the selection on screen. It applies registered keyword and empty-query routes and drops answers from earlier searches by generation.

`Action::Push` opens a view of the selected item's command with a fresh query. Browsing a folder uses the same navigation stack and searches the browser command. Esc closes an extension view and restores its parent query and selection. Backspace (⌫) returns to the previous view or folder when the query is empty. At the base of the stack, Backspace on an empty query returns to the registered default command.

Switching commands clears the previous rows. Generation checks reject late answers from the old command.

## Configuration changes

The resident panel owns the active configuration and hotkey binding; the Settings window reflects accepted values. One worker orders settings writes and watches the configured path and its symlink targets through the shared FSEvents watcher. Reloaded values use the same panel apply path as Settings and are never written back merely because they were read.

Each queued save has a revision. Reads carry the last revision the worker processed, and both views reject a snapshot older than the newest submitted save. Settings queues its panel update before submitting a save, so the worker's own file event cannot register the same hotkey twice. Parse and hotkey errors preserve the active values and remain visible without opening a window.

## Stored data

Data that must survive a restart without sitting on disk in the clear goes through `dupin-storage`, which has no OS dependencies. It gives each owner a namespace of sealed JSON records and content-addressed blobs with its own retention limits, and takes its data key from a `KeyProvider`: `dupin-mac::keychain::KeychainKey` on macOS, a private key file elsewhere, an in-memory key in tests. The host owns the files and the key; an extension reaches its own namespace only through the broker's `storage` capability, which the bridge opens with the quota and retention its declaration names. See [Encrypted storage](./features/storage.md).

`dupin-sync` syncs storage namespaces between Macs through a folder another tool keeps in step, such as iCloud Drive. It also has no OS dependencies: the vault key's stores (`dupin-mac::keychain::VaultKeychain` for this Mac's copy, `ICloudKeychain` for the synchronizable item in builds entitled to it) are supplied by the host. Every path in the folder is opened one component at a time without following links. See [Syncing Dupin between Macs](./design/sync.md).

## The panel

The panel is a Rune `launcher_panel`: a non-activating, retained panel that Rune draws ahead of time while hidden, so the hotkey only has to show it. The app is an accessory app (no Dock icon) that starts windowless and keeps running. The panel fits its content height, sits on Liquid Glass (`SystemMaterial::Glass`) under a light frost, and AppKit rounds it and draws its shadow. Behind the panel's content sits a Rune effect slot. A compositor (`backdrop.rs`) draws the backdrop shader into it: the built-in `flow` or a user's WGSL file. `shader.rs` wraps that file in Dupin's prelude and entry point and validates it with naga before it reaches the GPU. The compositor reads the shader's inputs (time since the panel showed, the last keystroke, the mode) from the panel state, and keeps frames coming only while the panel shows.
