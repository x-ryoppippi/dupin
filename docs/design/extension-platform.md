# Dupin extension platform

## Problem and goals

Before this design, Dupin had three ways to add features. Native features registered commands and providers, trusted script commands ran external programs, and an experimental Wasm runtime exposed a keyword, a bounded data protocol and a few host actions. The Wasm path required a guest toolchain and had no host imports, and it has since been removed (rollout step 4). None offered a small, typed package that an agent can write, run, inspect and test from text alone.

Give authors Raycast-style typed views, hot reload and useful diagnostics with a small native launcher footprint. Keep typing independent of extension work. A new extension starts with a query and a list. Built-ins remain complete with an empty config, and advanced users can combine them with extensions. Dupin renders every view and brokers access to the system. [Current extensions](../features/extensions.md) · [Script commands](../features/scripts.md) · [Raycast developer docs](https://developers.raycast.com/)

## Decision summary

- **QuickJS-ng via `rquickjs` is the single guest runtime.** A package is a directory with a `package.json` whose `dupin` key is the manifest, a JavaScript ES module and optional local assets. The default entry is `main.js`. The loader resolves relative package imports and the host's `dupin` module. A name, a version, a keyword and `search(query)` are sufficient.
- **Guests are compiled and run in a sandboxed, killable helper process, with QuickJS built at `-O3`.** The adoption gate showed that in-process limits cannot contain every guest, so the Dupin executable re-runs itself in an extension-host mode. The helper stays resident, talks to the app over a Unix socket, starts under a deny-by-default sandbox and is killed by an app-side watchdog when a compile or call overruns its deadline. It confines itself with `sandbox_init` when it starts, since an App Sandbox entitlement would also confine Dupin.app, lowers its resource limits, and the watchdog caps its physical footprint, which the heap limit alone overshoots. Each package is compiled in a helper started for that compile alone, since every later helper loads the bytecode unvalidated. A resident helper runs the searches and catalogues of one trust domain, one call at a time, so a kill fails only the call in flight. A helper answers each call's broker requests with the authority of the package that call runs, so a flaw exploited by one extension would act as every package that helper runs later: the bundled packages, which ship sealed with Dupin, share one helper, and every other package gets a helper of its own. Actions and events, which may wait on the network or a program far longer than typing can wait for that helper, each run in a helper of their own, as compiles do. The process boundary, not the engine, makes a call abandonable, so the `-Oz` latency trade-off no longer buys anything, and removing wasmi offsets the larger engine.
- **TypeScript runs as written when erasing its types is enough, and is built on the author's machine otherwise.** The extension host erases the types of `.ts` modules as part of its compile, in the sandboxed helper. A package with npm dependencies, or with syntax that needs a transform, is bundled by `dupin ext dev` and `dupin ext build` with the author's own Rolldown. Every package gets a `dupin.d.ts` declaration file. The host never type-checks.
- **Use one host contract.** Sources produce items, filters match, sort and convert them, and kinds supply actions. Native built-ins, such as app and file search, implement those interfaces in Rust; every built-in that needs no native API ships as a bundled TypeScript extension (see [Built-ins as bundled extensions](#built-ins-as-bundled-extensions)). Dupin owns the command registry, navigation, rendering and permissions. Settings shows feature switches and keywords. Recomposition lives in `[advanced]`.
- **wasmi is removed.** The Wasm implementation created no release compatibility obligation. Once JavaScript reached parity, its examples were ported and the Wasm guest loader, runtime, guest ABI and `extension.toml` manifest were removed together, carrying forward useful host schemas, limits and adversarial fixtures (rollout step 4). Trusted script commands remain available for any-language automation.
- **Packages are distributed through Git only.** `dupin ext install` fetches a tag or commit and records it in a lock file. Discovery is by the `dupin-extension` GitHub topic. There is no registry or reviewed store. See [Packaging and distribution](#packaging-and-distribution).
- **macOS only.** Windows is out of scope. A Linux port is deferred: the design keeps it in mind, but it is not planned now. See [Platform scope](#platform-scope).

All three designs converge on QuickJS-ng. Fable and Opus remove wasmi at parity; Astra would keep it for compute guests, but the owner has no compatibility obligation to it. [The adoption gate](../../experiments/js-runtime/README.md) measured native in-process QuickJS-ng, and it failed containment at both optimization levels. A native `String.prototype.indexOf` over a large haystack never polls the interrupt handler and ran past 10 s. Process footprint overshot the 16 MiB heap limit to 18.4 MiB, because the limit counts only QuickJS's own allocations. Only `-Oz` met the 1 MiB size gate, at about twice the warm latency of `-O3`. In process, a stuck call holds a worker thread indefinitely, and an engine or binding memory-safety flaw would compromise the Dupin process and its OS access. A helper process bounds both: the app can kill it at any instruction, and its sandbox withholds the app's authority. The broker stays in the app, which still grants and checks every capability. [Runtime discussion](https://github.com/x-ryoppippi/dupin/issues/6) · [Extension direction](https://github.com/x-ryoppippi/dupin/issues/96)

Author-side build with Rolldown | `dupin ext dev/build` runs the package's own Rolldown (`node_modules/.bin/rolldown`, else `rolldown` on `PATH`) and emits one plain ES module, optionally with source maps. The bundling scaffold (`dupin ext new --bundle`) pins Rolldown as a devDependency and ships the `rolldown.config.ts` that both `dupin ext build` and its GitHub Actions workflow use: ESM, `platform: "neutral"`, no code splitting, `dupin` external, and a resolver hook that fails on Node built-ins. ### Host-side erasure

The helper parses each `.ts`, `.mts` and `.tsx` module with oxc's parser and AST only (`oxc_parser`, `oxc_ast`, `oxc_ast_visit`, `oxc_allocator`, `oxc_span`, pinned to 0.157.0, without the parser's regular-expression feature) and replaces every type-only span with spaces of equal length, keeping line breaks. QuickJS then compiles the result under the module's own name, so diagnostics and stack frames carry the author's lines and columns and no source map exists. A `;` replaces an erased statement or class member, and follows `as T` when the next line starts with `(`, `[` or a template, so erasure never joins two statements; a multi-line arrow return type moves its `)` next to `=>`, and multi-line arrow type parameters move the `(` to their `<`, so `return`, `yield` and `async` keep their arrow on their line. Syntax that needs a transform (`enum`, including `declare const enum`, namespaces with values, parameter properties, decorators, JSX, `import =`, `export =`) is rejected as `typescript-needs-build`, naming the file, line and column, as is a `<T>value` assertion, which `erasableSyntaxOnly` also rejects because its erased type can end a `return` before the value. oxc's parser recurses at every level of nesting with no limit, so a module whose brackets nest past 1,000 levels is refused as `stack-limit` at that bracket before it is parsed, and the parse runs on a thread whose stack is sized to the source, so chains without brackets, such as `!!!…`, can't overflow it either. Erasure never runs in Dupin's process: Dupin only reads the files, and content hashing and bytecode reuse work on their text as for JavaScript. TypeScript files are modules only when `dupin.main` is one, so a bundled package's sources are never compiled.

Measured on 2026-11-24 on a Blacksmith macOS arm64 runner, with the release profile (`opt-level = "z"`, fat LTO, stripped; QuickJS at `-O3` as before):

| Measurement                                    |                    Value |
| ---------------------------------------------- | -----------------------: |
| Release `dupin` binary, before                 |         17,202,672 bytes |
| Release `dupin` binary, with erasure           |         17,485,296 bytes |
| Increase                                       | 282,624 bytes (0.27 MiB) |
| Erasing a 2,000-line, 86 KB module (p50 / p95) |        1.34 ms / 1.46 ms |

The increase is within the roughly 1 MiB the owner accepted and under Fable's 0.43 MiB estimate for a parser and blanking skeleton.

## Architecture

| Concept              | Placement in Dupin                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Source               | Adapt today's `Provider` behind a common interface. An `items()` source refreshes a catalogue on first use, invalidation or expiry. Rust filters cached candidates as the user types. A `search(query)` source owns matching for each query, as for a calculator or an OS index. Native providers keep their platform APIs. Native sources are registered by name in their feature's registration with the command they answer and the matcher they start with: `apps` and `folder` match their own candidates, while `files`, `files.contents` (Spotlight) and `recent` don't.                                                                                                                                                                                                                                                                                                                                |
| Filter               | Run a matcher, then a sorter, then a display converter per source. Reuse the native fuzzy scorer and usage history. Run guest stages only on bounded batches. Matchers select row IDs and highlights, sorters reorder existing IDs, and converters edit display fields. The host retains identity, payload and action authority. Reject matcher overrides that the source cannot support before candidate truncation. A native matcher implements `filter::Matcher` and is registered by name, `builtin.fuzzy` so far; a source without a matcher in its registration supports no override. Sorters and converters arrive with `[advanced]`: until then each native source keeps its own order and display.                                                                                                                                                                                                    |
| Kind                 | Register a typed payload and actions for it. Text, URL and file kinds centralize the action lists currently assembled by providers. The host resolves the action against the current row, installation and page. File actions use host-validated resource references. Native kinds are `text`, `url`, `file` and `app`: a source tags each row with a typed subject and the kind registered for it supplies the row's actions, its Enter and ⌘Enter, and its Send to… choices, so `kinds.<kind>.actions` has one list per kind to extend. Apps are their own kind rather than files, because they never offered the file actions (Open with…, Rename…, Move to Trash and the rest). An extension row's `text` and `url` resolve through the text and URL kinds; its `file` names a path the guest chose, not a host-validated reference, so it stays a display reference with none of the file kind's actions. |
| Host UI and commands | Compile feature defaults and advanced overrides into the existing command registry. `Session` still merges results, applies display limits, owns focus, restores selection on back navigation and drops stale generations. Rune renders the same bounded view model for built-ins and extensions.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

`features::MANIFEST` continues to own configure, prepare, start and reload. A registration supplies its providers, supported composition and default routes, plus the existing permission-use records. Migrate native features incrementally and preserve command IDs, keywords, usage history, pinned web results, fallback order and empty-query routes. The guest adapter registers a top-level `search` or `items` automatically. An advanced extension can declare named contributions in a `provides` object in its `dupin` key and export `sources`, `filters` or `kinds` maps. Dupin qualifies those local names with the installation's package ID. [ddu.vim architecture](https://raw.githubusercontent.com/Shougo/ddu.vim/main/doc/ddu.txt) · [Feature manifest](../../crates/dupin/src/features/mod.rs) · [Dupin architecture](../architecture.md)

The default `config.toml` can be empty. With `[advanced]` absent, the feature manifest supplies the full composition and the existing Settings toggles determine which features participate. For example, the files route keeps its native file actions and the main search uses the built-in app matcher. An advanced user can add a static bookmarks list, use prefix matching for apps and add an action without changing the other defaults:

```toml
[advanced.commands.default]
append_sources = ["bookmarks"]

[advanced.sources.apps]
matcher = "builtin.prefix"

[[advanced.kinds.file.actions]]
title = "Open in Zed"
script = "open-in-zed"
```

The configured script resolves to a user-installed command and receives the selected file only when invoked. Invalid references, conflicting keywords and incompatible payloads leave the last valid composition active. An extension that receives general search input needs separate consent. An extension filtering or acting on another producer's results receives only explicitly approved fields. The host keeps private payloads and file handles. A guest filter has no external effects or persistent state.

## Built-ins as bundled extensions

A built-in that needs no native API can ship as a bundled extension: a package in the repository's `extensions/<name>/`, written in TypeScript that the host runs after erasing its types, or JavaScript with `// @ts-check`, against `sdk/dupin.d.ts`, and type-checked in CI with `tsc --noEmit`. The Nix package copies each package folder into `Dupin.app/Contents/Resources/extensions`, read-only and inside the code signature, and `scripts/package-app.nu` signs that copy as it is. A build run from the source tree reads `extensions/` directly. The build seals the bundled packages: `crates/dupin/build.rs` compiles the content hash of each package folder into the binary, and a bundled folder that isn't one of them or no longer matches stays off, so trust in a bundled package rests on the binary, not on where a folder sits. Bundled packages run through the same extension host and limits as any other.

| Decision  | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Discovery | Bundled packages are always scanned. A package in the user's extensions folder with the same `name` replaces the bundled one while that folder is on; deleting it restores the bundled one. Bundled packages register first, and the folder's packages wait until the bundled scan has landed, so a user package never takes a bundled keyword. `dupin ext install` refuses a bundled name or keyword.                                                                                                                                                                                            |
| Identity  | A package's revision is a hash of its manifest bytes and its guest code. The broker knows a bundled package as `bundled:<name>` and registers each bundled revision with its bundled mechanism, so the package is on by default and its declared extension capabilities are pre-granted exactly while that revision is active. A copy with the shipped revision is that package. A changed copy is another revision under its plain name, so it is third-party: it runs as any package in the folder does, with nothing pre-granted and none of the bundled package's grants, consents or switch. |
| Editing   | `dupin ext eject <name>` copies a bundled package into the extensions folder with writable files. Settings → Extensions marks it as an unchanged or changed copy.                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Switches  | Settings → Extensions lists bundled and user packages with a switch each, saved through the broker in `grants.toml`. A bundled package runs while the broker has it enabled; a package in the folder runs while the folder is on, unless its switch is off. OS permissions still follow [#12](https://github.com/x-ryoppippi/dupin/issues/12): bundled grants never imply macOS access, and only turning on a bundled package that ships off requests what its grants need, as the feature switch it stands in for would.                                                                         |

Ports of native features keep their existing feature switches and command IDs; each port decides how its switch maps onto the package's enablement. A built-in the owner decided isn't core becomes an optional bundled extension instead: it has no feature switch, ships off and waits for its own switch in Settings → Extensions, and its package is the whole feature. Discussion: [#218](https://github.com/x-ryoppippi/dupin/issues/218).

| Built-in            | Runs as                                         | Why                                                                                                                                                                                                                                                                        |
| ------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| App and file search | Native sources and kinds                        | They match on every key against platform indexes (LaunchServices, Spotlight) and own the default route.                                                                                                                                                                    |
| Calendar search     | Bundled extension behind its existing setting   | Reading events is the `calendar` service; formatting and grouping them needs no native API.                                                                                                                                                                                |
| Clipboard history   | Bundled extension behind its existing setting   | Watching copies is the `clipboard` service, and the package keeps them, images included, in its own encrypted storage under its retention preference; Dupin matches its catalogue natively and draws image thumbnails from that storage without passing them to the guest. |
| Dictionary          | Bundled extension behind its existing setting   | Looking words up is the `dictionary` service; laying out an entry needs no native API.                                                                                                                                                                                     |
| Snippets            | Bundled extension behind its existing setting   | Dupin hands the shipped package the snippets from `config.toml` as preferences; it lists them with `items()`, and Dupin fills a template's placeholders when one is copied or pasted.                                                                                      |
| Web search          | Bundled extension, on                           | Dupin hands the shipped package `web_searches` and `web_fallbacks` from `config.toml`; it lists them as web search items, whose aliases Dupin matches and whose URLs it fills natively, so typing never waits on the guest.                                                |
| Emoji & Symbols     | Bundled extension, on                           | A static catalogue, with nothing native to replace.                                                                                                                                                                                                                        |
| Dupin               | Bundled extension, on                           | Links to Dupin's documentation, issues and source, with nothing native to replace.                                                                                                                                                                                         |
| Window management   | Optional bundled extension, off until turned on | The owner decided it isn't core. Its commands are actions, not per-keystroke search, so frames are computed in the guest and only reading and moving the focused window is native, through the `windows` service, with Accessibility asked for when the user turns it on.  |

A port that answers typing is held to the latency of the native feature it replaces. Before the native implementation is removed, `scripts/latency/native-baseline.json` records what the Latency workflow measured of it at its last commit, and the workflow fails when the bundled extension's p95 exceeds that baseline by more than the larger of 10% and 0.5 ms. Window management runs only when a command is chosen, so it has no latency scenario.

## Example extensions

### A query in, a list out

`package.json`

```json
{
	"name": "word-count",
	"version": "0.1.0",
	"dupin": { "title": "Word Count", "keyword": "wc" }
}
```

`main.js`

```js
export function search(query) {
	const input = query.trim();
	if (!input) return [];

	const count = input.split(/\s+/u).length;
	const title = `${count} words`;
	const text = String(count);

	return [{ title, text }];
}
```

Type `wc two words` to see **2 words**. Enter copies `2`. The two files above are the complete extension.

### A list source

Use the same manifest shape with `"name": "bookmarks"`, `"title": "Bookmarks"` and `"keyword": "bm"`. Replace the entry with `items()`. Dupin caches the rows by their `id` and supplies URL actions and native matching.

```js
export function items() {
	return [
		{ id: 'dupin', title: 'Dupin', url: 'https://github.com/x-ryoppippi/dupin' },
		{ id: 'rune', title: 'Rune', url: 'https://github.com/x-ryoppippi/rune' },
	];
}
```

### A pushed view with a capability

Add the following `capabilities` entry to the bookmarks `dupin` key and append the handler below to its entry. Add `actions: [{ title: "Repository status", push: { view: "repository" } }]` to the Dupin row. Selecting that action opens a host-rendered Detail page. The entry requests HTTP access only for the declared origin and method.

```json
"capabilities": {
	"http": [{ "origin": "https://api.github.com", "methods": ["GET"] }]
}
```

```js
import { http } from 'dupin';

export const views = {
	async repository() {
		const response = await http.fetch('https://api.github.com/repos/x-ryoppippi/dupin');
		if (!response.ok) throw new Error(`GitHub returned ${response.status}`);
		const repo = await response.json();
		return {
			type: 'detail',
			title: 'Dupin',
			markdown: repo.archived ? '**Archived**' : 'Active repository',
		};
	},
};
```

An offline fixture drives the selected action and returns a synthetic `200` with `{"archived": false}`. The expected view contains `Active repository`. The same fixture can exercise denial and revocation without touching GitHub.

## API and UI components

| API                                  | Contract                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `search(query, ctx)` or `items(ctx)` | A synchronous or async array of items or a List object with optional sections and empty-state text. Items have a title, optional stable ID, subtitle, icon, keywords and kind data. The host applies schema and output limits and preserves the relative order of query results by default.                                                                                                                                                                                                 |
| `views[name](ctx)`                   | Returns List, Detail or Form. `ctx` holds read-only preferences, the current page query and bounded JSON state. A fresh invocation makes module globals transient.                                                                                                                                                                                                                                                                                                                          |
| `actions[name](data, ctx)`           | Runs on explicit activation, including form submit. Returns a bounded effect such as push, pop, refresh, replace state, toast, or field errors. Named handlers and their data are resolved against the active page. Simple Copy, Paste, Open URL and Push can be declared directly as data; Paste needs the package's granted `clipboard:paste` scope and Accessibility, and copies otherwise.                                                                                              |
| Preferences and state                | Manifest preferences are checkbox, select and number fields with defaults; a built-in's Settings rows supply its package's values. A text field is planned. Missing required values lead to Settings. `Session` owns per-page state and commits only the current generation. Saved presentation is inert. Resuming a page revalidates package identity, state compatibility and grants. Persistent data uses the `storage` capability; defer secret preferences until a feature needs them. |

The initial component set is deliberately small. What ships today is the List with sections, icons, images and a selected-item Detail pane, item actions and `actions`/`events` handlers; `views`, `push`, Form and accessories are drafted only as types in the SDK's `planned` namespace (rollout step 7).

| Component    | Supported surface                                                                                                                                              |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| List         | Labeled sections, title/subtitle, built-in icons, up to three text or tag accessories, two-value answer rows and an optional selected-item Detail pane.        |
| Detail       | Title, labeled metadata and bounded Markdown with headings, paragraphs, emphasis, lists, inline/fenced code and HTTP(S) links. Dupin handles link activation.  |
| Form         | Text, multiline text, checkbox and single-select. Dupin owns drafts, tab order, required-field validation and submit/cancel. Guest validation runs on submit.  |
| Action panel | Primary and secondary actions, up to eight guest actions per item. Enter invokes the primary. Right or ⌘K opens the panel. Dupin confirms destructive actions. |
| Status       | Empty text, host loading and error states, access recovery, one transient toast after an action and a brief HUD when the action closes the panel.              |

Grids, charts, custom styling, JSX/React, webviews, HTML and remote media would add another rendering or network surface. Background execution, menu-bar items, arbitrary key bindings and guest focus control would add separate lifecycle and interaction policies. Defer them. A component needs a keyboard interaction and a deterministic renderer fixture before it is added. [View and state discussion](https://github.com/x-ryoppippi/dupin/issues/7)

## Capabilities and consent

The broker exposes `http`, `exec` (including `@script` targets), `files`, `storage`, `clipboard` (`read`, `write`, `watch` and `paste`), `dictionary`, `calendar` and `windows`; [Capability broker](../capability-broker.md) lists each scope. The manifest declares the maximum scope. A Dupin-owned store persists user grants against the installation and approved revision. A manifest or config reload cannot grant access. The broker checks enablement and scopes at dispatch and before delivering results. Query handlers may use approved bounded reads. Mutations and trusted native tool invocations require a host-verified user activation. The broker owns user-facing errors, cancellation and output bounds.

| Capability | Scope and enforcement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `exec`     | A named profile binds a user-selected executable to an argument template and working directory. Validate typed inputs, use argv without a shell and supply a minimal environment. Reuse script-runner process cleanup. An `@script:<name>` target binds to a specific user-installed script command and invokes the trusted runner. Returning script output to the guest requires explicit approval. Both targets run with native user authority and may use their own credentials or hooks. Show the command and that consequence in consent. |
| `http`     | Explicit HTTPS origins and methods. Validate redirects and resolved destinations, block private addresses by default and cap time and response size. Supply no ambient cookies or authentication.                                                                                                                                                                                                                                                                                                                                              |
| `files`    | Named user-picked file or directory scopes. Start with read/list. Validate the opened resource within the allowed root, including symlink and race handling. Add writes separately when needed.                                                                                                                                                                                                                                                                                                                                                |

Plain HTTP(S) Open and Copy actions use existing host validation and a deliberate selection. The OS-backed capabilities (`clipboard`, `dictionary`, `calendar`, `windows`) and `storage` are documented with the extension API in [Extensions](../features/extensions.md). A later outbound `mcp` capability can bind an exact tool on a user-configured server to the approved server identity and schema. Require activation for each call, validate input and bound output and lifetime. The host owns connection credentials and transport. Default-search input and cross-producer fields each require a separate scoped consent decision before guest composition can expose them.

1. **Enable.** New installations start off. Deliberately enabling one shows its requested scopes and lets the user grant them individually. Dupin.app requests any still-undetermined macOS access needed for a selected scope. First deliberate use can request access if configured outside Settings. Startup, Settings open, reload, background search and fixtures only inspect status.
2. **Explain.** Build Settings → Permissions from the existing `features::permission_uses()` and validated extension declarations. Show each OS permission once and list its consumers and extension grants. **Request Access** can ask macOS on behalf of Dupin with a feature off. That OS decision grants no extension authority by itself. Offer **Open System Settings** after denial and refresh access on focus and prompt completion.
3. **Revoke.** Scope each grant to the installed package and approved revision. Disable or revoke immediately, cancel owned work where possible, drop pending completions and invalidate derived caches and actions. Reapproving a grant cannot revive old completions. Previously completed external effects may survive. Reuse the existing policy's invalidation semantics behind the broker. Keep installation IDs and revisions out of the author API. [Current permission policy](../features/permissions.md) · [Capability broker](../capability-broker.md) · [Owner decision](https://github.com/x-ryoppippi/dupin/issues/12)

## Packaging and distribution

The manifest is the `dupin` key of `package.json`. It is static JSON, so Dupin reads the requested capabilities, keyword and entry without running guest code, and authors keep the file their JS tooling already uses. There is no separate manifest file and no manifest generated from code.

Authors use npm dependencies freely and bundle them at build time. The installed entry is one self-contained ES module. A build fails when a dependency needs Node built-ins such as `fs` or `net`, which do not exist in the guest.

Packages are distributed through Git, not a package registry:

| Source | Example                                                  | Behavior                                                         |
| ------ | -------------------------------------------------------- | ---------------------------------------------------------------- |
| Git    | `dupin ext install github:user/repo@v1` or `@<commit>`   | Fetches the tag or commit and records the resolved commit SHA.   |
| Local  | `dupin ext install ./word-count`, or `dupin ext dev ./…` | Loads the folder in place, for authoring and private extensions. |

- **Built JS is committed.** Plain JS and erasable TypeScript need no build. A bundled package commits its built entry, as GitHub Actions do. The `dupin ext new --bundle` scaffold includes a workflow that rebuilds and commits it on push. An install never runs a package manager, install scripts or a build. A package without its built entry fails with a diagnostic.
- **Pinning.** A lock file records each package's source, resolved commit SHA, content hash and granted scopes. Installed contents change only through `dupin ext update`, which moves to the newest tag, or the default branch when the repository has no tags. An update that adds scopes asks again. Removed scopes are dropped.
- **Nix.** Home Manager declares packages with `fetchFromGitHub` and their grants. That configuration is the read-only base, and local grant choices overlay it in the writable data directory, as `config.toml` and `settings.toml` do.
- **Discovery.** Dupin lists GitHub repositories with the `dupin-extension` topic through the GitHub API. There is no reviewed store, hosted index or publishing account. Listings show each package's requested capabilities, read from `package.json` on the default branch, because the broker, not a review, protects users. Listings are marked unreviewed, all listed text is untrusted and shown as plain bounded text, and listing never installs.

npm publishing, a curated index repository and a reviewed store stay out of scope until real use shows a need.

## Performance budget and gates

Use the existing provider workers and generation checks. The app starts the extension host on first guest use and keeps it resident. The app never parses, compiles or runs guest JavaScript: QuickJS's parser and bytecode emitter are part of the engine and are reachable from package source, and parsing never polls the interrupt handler. When the app loads or reloads a package revision, it reads the manifest and source files itself, applies source size limits and sends the source to a helper started for that compile alone, which compiles every module under the same deadline, limits and watchdog as a call. The helper returns the bytecode or diagnostics. The app caches the bytecode keyed by package revision and content hash as opaque bytes that it never interprets, and sends them back with each invocation and its query. QuickJS bytecode is not validated, so only the helper loads it, and a package can never supply it. The helper replies with bounded rows or broker requests, which the app validates as untrusted. Inside the helper, each compile and each invocation gets a fresh QuickJS runtime and context with no ambient filesystem, process or network APIs, and the sandbox denies them at the OS level as well. Cache validated static results in the host view format. Start with 16 MiB heap and 512 KiB stack limits per invocation, four concurrent guest calls across the app and bounded request, result and job queues. Enforce a monotonic deadline while compiling or loading the module, executing code, pumping promise jobs and encoding results. Start with the existing two-second search deadline as the outer containment limit and tune the active execution budget against the prototype. The QuickJS interrupt ends ordinary overruns in place. When a compile or call is still running at the outer limit, the app's watchdog kills the helper, fails that compile or call and restarts the helper on the next guest use. Resolve broker operations asynchronously. Coalesce superseded jobs, cancel pending operations and drop late results, including those from replaced revisions. Shed guest load independently of native providers.

## Platform scope

Dupin targets macOS. Windows is out of scope. A Linux port is deferred: it is kept in mind, so the guest contract, helper mode, socket protocol, fixtures and limits stay free of macOS assumptions, but it is not planned now. The sandbox is macOS-only (`sandbox_init`), and on any other platform the host refuses to compile or run extensions with `sandbox-unavailable`, so a port would need its own confinement for the helper before any extension runs there. Executable resolution, file handles, process cleanup, clipboard and permissions stay in platform adapters, and macOS uses Dupin.app for TCC. [Linux PR #166](https://github.com/x-ryoppippi/dupin/pull/166)

## Sync

Sync between the owner's Macs is a host service on `dupin-storage` namespaces, through a user-chosen synced folder with end-to-end encryption and no Dupin server. Built-ins such as snippets and clipboard history get it by declaring a sync mode for their namespace. An extension's `storage` namespace syncs only with a `storage.sync` scope that the user grants on each Mac, and the extension list syncs from the lock file while grants are re-consented on each Mac. [Sync design](./sync.md)

## Rollout

1. Measure native QuickJS-ng in `experiments/js-runtime`. Done: in-process execution failed containment, so guests move to a helper process.
2. Ship keyworded `search(query)` with the existing row and push semantics, JS scaffold and directory-based `check`/`run`. Add adversarial fixtures and the word-count port. Verify parity for copy, URL open, pushed lists and details, navigation and diagnostics. Done, except pushed lists and details, which moved to step 7 when the Wasm runtime, their only guest, was removed.
3. Move guest compilation and execution into the sandboxed extension-host helper with its watchdog, so the app keeps only opaque cached bytecode, and build QuickJS at `-O3`. Rerun the experiment's containment fixtures and the latency gates through it, including compile-time fixtures, the helper round trip and kill and restart. Done: the helper compiles and runs every package, the app keeps only opaque bytecode, and on a Blacksmith M4 runner starting the helper and compiling a 400-candidate package took 12.0 ms at p95, and a warm 50-row query 1.8 ms at p95. The helper tests run outside the Nix build sandbox in CI, since macOS refuses `sandbox_init` inside it.
4. Port the remaining Wasm examples and fixture coverage and remove wasmi and the guest ABI once parity and release gates pass. Done: the word counter and the Wasm runtime's startup-loop and startup-allocation fixtures are JavaScript, and the Wasm loader, runtime, `extension.toml` manifest and `dupin ext check`/`snap` module forms are gone. A leftover `extension.toml` is reported as removed. Pushed views had no other guest, so they wait for step 7. On a Blacksmith M4 runner the ad-hoc-signed app binary from `nix build` shrank by 633,584 B (17,236,336 to 16,602,752 B) and its ZIP by 309,860 B.
5. Add the author-side `dev`/`build` pipeline and declarations. Share the renderer with `snap` and add fixture-driven `test` as a separate PR. Expose those fixture operations through MCP once they are stable. Done: fixtures are a versioned format whose replies stand in for every host service behind the real broker; `test` replays them through the sandboxed host with a fixed clock, seed and time zone, `snap` renders the production panel headless, and `dupin mcp --workspace` offers both. `snap` answers host requests from the fixture's replies through the broker, as `test` does, and `test` replays `items()` catalogues and their updates with the launcher's matcher. Rune's headless tooling ships in the release app, which it grows by 33,488 B (19,314 B zipped) on a Blacksmith M4 runner, so authors snap with the Dupin they run.
6. Adapt apps and files to native sources and kinds. Add cached `items()` and shared matchers with default-route regression coverage. Port other built-ins individually. Cached `items()` done: Dupin holds each package revision's catalogue in memory and matches it with the apps matcher and usage ranking, with `ttl`, parts, updates by ID and invalidation from an action or event handler, and a manifest flag lists it in the main search. A catalogue reaches host services through the broker as a search does, under the query trigger, and belongs to the generation it was read under, so lost authority drops it; clipboard history is a catalogue read from storage that a `clipboard.watch` handler updates. Catalogues are not persisted; a package that wants its list to outlast a restart keeps it in its own storage. The 5,000-item latency fixture and the parity helper are ready for the ports. Calendar search is the first port: the bundled `calendar` package answers the feature's command and keyword behind its existing switch, reads events through the `calendar` service, which writes their dates in the Mac's locale for a guest without `Intl`, and held native parity before the native search was removed. Clipboard history is the second: the bundled `clipboard-history` package keeps each watched copy in its storage and hands Dupin a catalogue it matches by words, updated by prepending and removing entries, and held native parity on a 5,000-copy history before the native history was removed. Snippets followed: the bundled `snippets` package lists the snippets from config.toml with `items()`, which Dupin checks and hands only the package it shipped in `ctx.preferences`, beside the preferences its manifest declares; its copy and paste actions are templates whose placeholders Dupin fills when one is chosen, a snippet's keyword is an `alias` that ranks as its name does, and it held native parity before the native provider was removed. Dictionary is ported the same way: the bundled `dictionary` package answers its command and aliases through the `dictionary` capability, which also returns the native layout as Markdown, and the native provider is gone; its latency scenario is held to the native results recorded before the removal. Window management left the core: the bundled `window-management` package, off until the user turns it on, computes each command's frame from the displays and moves the focused window through the `windows` service, whose `arrange` scope needs an activation. Its commands run only when chosen, so it has no latency scenario; the 5,000-item catalogue fixture already bounds what its ten catalogue rows cost the main search. Web search done: catalogue items can be web searches (an alias and a URL template) that Dupin matches and fills natively, and Dupin hands config.toml's `web_searches` and `web_fallbacks` to the `web-search` package it shipped through `ctx.preferences`, beside any preferences it declares; the native provider is gone. Before it went, `web.rust` measured p95 2.05 ms native and 2.06 ms with the extension on a Blacksmith M4 runner. Apps and files done: app search, Spotlight file and content search, folder browsing and recent items are native sources whose feature registrations name them, the matcher they start with and the command they answer; their rows' actions and Send to… come from the `file` and `app` kinds instead of each provider, and extension rows' copy and open actions from the `text` and `url` kinds. Every action list, default route and ranking is unchanged. On a Blacksmith macOS runner, three alternating runs of the main search scenarios before and after kept their p95 within the runs' own spread (`search.saf` 2.28 ms before and 2.49 ms after at the median, `search.term` 2.51 and 2.60 ms, while the untouched `search-catalogue.term` moved by as much, 3.14 and 3.34 ms), and building a file row took 1.36 µs instead of 1.41 µs. Spotlight indexing is off on the runners, so file search has no latency scenario.
7. Add the fixed UI in small slices, starting with sections and Detail, then host-held page state, Form and action outcomes. Partly done: list sections, a selected-item Detail pane, images, item actions and `run` actions with toasts ship; pushed views, host-held page state, Form and accessories are drafted only in the SDK's `planned` namespace.
8. Ship the broker with a scoped HTTP read and its full consent, cancellation, revocation and Permissions page flow. Add scoped files and executable profiles with `@script` targets in separate PRs. Done: the broker grants `http`, `files` and `exec` with `@script` targets, and the ports added `storage`, `clipboard`, `dictionary`, `calendar` and `windows`; consent is asked in the panel and in Settings → Extensions, which also revokes. An outbound `mcp` capability is not planned yet.
9. Add advanced configuration with native filters and actions first. Enable third-party kinds and filters only after cross-producer scopes and limits are enforced. Add Git installs, the lock file, updates, the Home Manager module and topic-based discovery. Partly done: `dupin ext install`, `update` and `remove` with the lock file, and the Home Manager module's `programs.dupin.extensions`, ship. Topic-based discovery is done in the CLI: `dupin ext search [QUERY]` lists the `dupin-extension` repositories GitHub's search API returns, up to 20 with the most stars, each with its owner, description, stars, last push, the scopes its default branch's `package.json` requests and its `dupin ext install github:owner/repo` line. Settings has no discovery list. `[advanced]` configuration and third-party kinds and filters are not built; the native sources, matchers and kinds they will compose are (step 6).
